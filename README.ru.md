Codex Harness — локальная система контроля изменений вокруг Codex. Она сохраняет состояние до редактирования, анализирует результат, сравнивает два набора диагностик и разрешает или блокирует дальнейшую работу по детерминированным правилам.

Промпты, навыки и инструкции модели направляют Codex. Harness обеспечивает выполнение реализованных проверок через обработчики событий, исходные снимки, запуск анализаторов, определение регрессий и лимиты повторных попыток. Автоматические проверки архитектуры и зависимостей между слоями приложения остаются в плане развития.

Harness подключает Ruff, Flake8, Pylint, Black и MyPy как внешние анализаторы. Они возвращают диагностики и метрики; Harness определяет, являются ли эти результаты регрессией.

## Обзор и жизненный цикл

Контрольный путь выглядит так:

```text
Codex → Hooks → Harness → Analyzers → Findings → Regression Policy → Allow / Block
```

Текущая интеграция использует два обработчика событий Codex (hooks) вокруг `apply_patch`:

- `PreToolUse` определяет область выполнения, проверяет бюджет повторных попыток и сохраняет исходный снимок затрагиваемых Python-файлов;
- `PostToolUse` анализирует снимок и получившийся исходник, нормализует результаты анализаторов и применяет политику регрессий.

```text
Codex запрашивает apply_patch
          |
          v
PreToolUse hook
  +-- лимит попыток исчерпан? -----------------------> блокировка до изменения
  +-- сохранить снимок ДО
          |
          v
apply_patch изменяет файлы
          |
          v
PostToolUse hook
  +-- запустить подключённые анализаторы для ДО и ПОСЛЕ
  +-- нормализовать метрики и диагностики
  +-- применить общую политику регрессий
          |
          v
Сравнение регрессий
  +-- новых или ухудшившихся диагностик нет ---------> разрешить
  +-- есть регрессия --------------------------------> блокировка и отчёт в Codex
                                                         |
                                                         +-- Codex может исправить
                                                         +-- лимит попыток остановит новые патчи
```

Сейчас реализованы проверки качества Python. Та же граница проверок предназначена для будущих правил архитектуры и зависимостей без привязки управления жизненным циклом к конкретному анализатору. Проверки ООП и зависимостей между слоями приложения пока не реализованы.

## Политика регрессий

Harness оценивает изменение Codex, а не весь накопленный технический долг целевого проекта. Существующие диагностики входят в исходный снимок и сами по себе не блокируют несвязанное изменение.

```text
старый технический долг != ошибка Codex
новый технический долг  = регрессия
ухудшение старого кода   = регрессия
```

Например, неизменившаяся функция с 63 инструкциями допускается, а рост с 63 до 70 считается регрессией. Новая функция, которая сразу превышает лимит, также считается регрессией.

Числовые метрики (`CFQ001`, `C901`, `PLR0912`, `PLR0915` и `PLR1702`) сравниваются по файлу, анализатору, правилу и полному имени функции. Новое превышение лимита или рост значения блокируется. Уменьшение существующего превышения, например с 82 до 81 строки при лимите 80, допускается. Перенос функции на другие строки в том же файле не создаёт регрессию.

Обычные диагностики анализаторов сравниваются по файлу, анализатору, коду, тексту сообщения и количеству повторений. Существующий `F401` остаётся частью исходного состояния; дополнительное вхождение той же диагностики считается регрессией. Долг в одном файле или анализаторе не компенсирует новое нарушение в другом. Синтаксические ошибки изменённого исходника считаются ошибками кода. Инфраструктурные ошибки блокируют операцию, но не расходуют бюджет исправлений кода.

## Инструменты, анализаторы и диагностики

Конфигурация определяет, какие анализаторы и правила запускаются. По умолчанию включены Ruff и Flake8, которые предоставляют следующие числовые метрики:

| Метрика | Правило | Анализатор | Лимит по умолчанию |
| --- | --- | --- | ---: |
| Физическая длина функции | `CFQ001` | Flake8 + `flake8-functions` | `80` |
| Сложность функции | `C901` | Ruff | `10` |
| Ветвления | `PLR0912` | Ruff | `12` |
| Инструкции | `PLR0915` | Ruff | `50` |
| Вложенные блоки | `PLR1702` | Ruff | `4` |

Эти правила измеряют разные свойства. В частности, физические строки и инструкции независимы: пустые строки и комментарии могут влиять на `CFQ001`, но не являются инструкциями для `PLR0915`. Семантику правил определяет анализатор; Harness не содержит их параллельных реализаций.

Если выбран `CFQ001`, Flake8 запускает его в изолированном проходе Harness. Плагин `flake8-functions` измеряет длину, а Harness связывает результат с полным именем функции. Конфигурация Flake8 целевого проекта и `noqa` не отключают выбранную метрику.

Когда Ruff включён, он вычисляет остальные четыре числовые метрики в изолированном проходе с лимитами из `~/.codex/harness/config/quality.toml`; для этого прохода включён режим preview. Отдельный проход обычных правил учитывает `use_project_config` и выбранные наборы правил. По умолчанию он использует настройки проекта и добавляет `PLC0415`. Числовые диагностики сравниваются только один раз. Лимиты метрик проекта не заменяют лимиты Harness, а прямой ручной запуск Ruff использует настройки самого проекта.

Ruff, Flake8, Pylint, Black и MyPy реализуют общий интерфейс анализатора. Запускаются только инструменты с `enabled = true`. Адаптеры отвечают за запуск процессов и разбор вывода конкретных инструментов; оркестрация и обработчики событий работают с нормализованными результатами. Новый анализатор можно добавить без изменения обоих обработчиков.

Диагностики Pylint и MyPy используют ту же политику сравнения количества вхождений, что и обычные диагностики Ruff. Black только проверяет форматирование и не изменяет исходники: уже неформатированный файл остаётся допустимым исходным состоянием, а новая регрессия форматирования блокируется.

Ссылки на правила: [`CFQ001`](https://github.com/best-doctor/flake8-functions), [`C901`](https://docs.astral.sh/ruff/rules/complex-structure/), [`PLR0912`](https://docs.astral.sh/ruff/rules/too-many-branches/), [`PLR0915`](https://docs.astral.sh/ruff/rules/too-many-statements/), [`PLR1702`](https://docs.astral.sh/ruff/rules/too-many-nested-blocks/).

## Архитектура Harness и структура проекта

```text
codex-harness/
├── hooks/                   # обработчики событий, области выполнения и попытки
├── checks/                  # общие проверки и жизненный цикл снимков
│   ├── config/              # схемы, загрузка, валидация и миграция
│   ├── code_quality/        # общий CLI проверки качества
│   ├── analyzers/           # контракт адаптеров, каталог, реестр и оркестрация
│   │   ├── ruff/            # диагностика, метрики и отдельный Ruff CLI
│   │   ├── flake8/          # диагностика Flake8 и метрика CFQ001
│   │   ├── pylint/          # интеграция Pylint
│   │   ├── black/           # проверка форматирования
│   │   └── mypy/            # проверка типов
│   ├── snapshots/          # сохранение, хранение и сравнение до/после
│   ├── regression.py       # общая политика количества нарушений и метрик
│   ├── storage.py          # атомарное сохранение файлов
│   └── symbols.py          # квалифицированные имена символов
├── config/quality.toml      # копия конфигурации в репозитории
├── src/codex_harness/       # метаданные пакета и встроенные настройки
│   └── defaults/quality.toml # актуальный шаблон настроек по умолчанию
└── pyproject.toml
```

Актуальный шаблон настроек по умолчанию — [src/codex_harness/defaults/quality.toml](src/codex_harness/defaults/quality.toml); он входит в пакет. Файл `config/quality.toml` в корне репозитория — отдельная копия, а не шаблон установки. При выполнении конфигурация читается из пользовательского пути ниже независимо от расположения клонированного репозитория.

После установки исполняемый код загружается из Python-пакета и не зависит от клонированного репозитория. Пользовательские данные хранятся отдельно:

```text
~/.codex/harness/
├── config/quality.toml
└── state/retry/<scope_hash>/
```

Отсутствующий `quality.toml` создаётся автоматически из встроенного шаблона. Прежняя конфигурация `[python.*]` атомарно мигрирует в версионированную схему `[tools.*]`, а исходный файл сохраняется как `quality.toml.v0.bak`. Версионированные файлы не переписываются; отсутствующие параметры получают текущие значения по умолчанию.

### Ответственность внутри `checks/`

`checks/` задаёт границу между политиками Harness и анализаторами. Он преобразует вывод инструментов в нормализованные диагностики и сравнивает их, не перенося специфику конкретных инструментов в обработчики событий.

| Модуль | Ответственность |
| --- | --- |
| `config/` | Загружает и валидирует конфигурацию, предоставляет настройки по умолчанию и мигрирует прежние пользовательские настройки. |
| `code_quality/` | Предоставляет общий CLI проверки качества. |
| `analyzers/` | Определяет нормализованные диагностики и общий контракт адаптеров; запускает настроенные анализаторы. |
| `analyzers/<tool>/` | Владеет конфигурацией, запуском, разбором и нормализацией вывода конкретного инструмента. |
| `regression.py` | Сравнивает количество нарушений и числовые метрики через единую политику, независимую от анализаторов. Долг относится к своему файлу и инструменту. |
| `snapshots/` | Сохраняет и потребляет снимки, получает исходники до/после и координирует анализ с политикой регрессий. |
| `storage.py`, `symbols.py` | Обеспечивают атомарное сохранение и квалифицированные имена символов соответственно. |

Числовые метрики и обычные диагностики сравниваются по разным правилам: превышенная метрика может улучшиться, не достигнув лимита, а обычные нарушения отслеживаются по количеству повторений. Нормализация внутри адаптера обрабатывает особенности инструмента, например сводит несколько отчётов `PLR1702` для одной функции к максимальному значению, вычисленному Ruff.

Все импорты используют пространство имён `codex_harness`. Для ручного запуска и обработчиков событий используются установленные консольные команды; прежние способы запуска через пути к файлам не поддерживаются.

## Требования

Рекомендуется:

```text
Python 3.12+
Codex CLI с поддержкой lifecycle hooks
```

Проверить Python:

```bash
python3 --version
```

`pip install .` устанавливает полный набор анализаторов. Отдельно устанавливать линтеры не требуется. Посмотреть установленные версии можно командами:

```bash
python3 -m flake8 --version
python3 -m ruff --version
python3 -m pylint --version
python3 -m black --version
python3 -m mypy --version
```

Совместимые диапазоны версий, включая `flake8-functions`, записаны как прямые зависимости пакета в `pyproject.toml`. Harness запускает все инструменты через тот же Python, в который установлен пакет.

## Установка

Клонировать исходники в любой временный или постоянный каталог и установить пакет:

```bash
git clone https://github.com/r-tatarinov/codex-harness.git
cd codex-harness
python3 -m pip install .
```

После установки клонированный репозиторий не нужен для выполнения Harness. Найти абсолютные пути консольных команд:

```bash
command -v codex-harness-pre-tool
command -v codex-harness-post-tool
```

## Подключение к Codex

Создать глобальный файл:

```text
~/.codex/hooks.json
```

Пример:

```json
{
  "description": "Central local Codex harness",
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "^apply_patch$",
        "hooks": [
          {
            "type": "command",
            "command": "/absolute/path/to/codex-harness-pre-tool",
            "timeout": 10,
            "statusMessage": "Saving code quality baseline"
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "^apply_patch$",
        "hooks": [
          {
            "type": "command",
            "command": "/absolute/path/to/codex-harness-post-tool",
            "timeout": 30,
            "statusMessage": "Checking code quality regression"
          }
        ]
      }
    ]
  }
}
```

Пути в примере необходимо заменить результатами `command -v`. Старые команды через `hooks/pre_tool.py` и `hooks/post_tool.py` не поддерживаются.

После изменения `hooks.json` необходимо полностью перезапустить Codex.

При первом запуске Codex покажет:

```text
Hooks need review
```

Необходимо проверить обработчики и разрешить их выполнение.

После запуска состояние можно посмотреть командой:

```text
/hooks
```

Должно быть активно:

```text
PreToolUse     1 installed / 1 active
PostToolUse    1 installed / 1 active
```

## Настройка инструментов и правил

Все переключатели инструментов, правила, лимиты и поддерживаемые параметры находятся в:

```text
~/.codex/harness/config/quality.toml
```

Если пользовательская конфигурация отсутствует, первая загрузка настроек создаёт её из встроенного шаблона [src/codex_harness/defaults/quality.toml](src/codex_harness/defaults/quality.toml). В схеме версии `1` лимит повторных попыток хранится в `[verification]`, а настройки анализаторов — в `[tools.<name>]` с подсекциями `rules`, `limits` и `options`. Основная часть конфигурации по умолчанию:

```toml
schema_version = 1

[verification]
max_attempts = 3

[tools.ruff]
enabled = true
use_project_config = true
timeout_seconds = 10

[tools.ruff.rules]
extend_select = ["PLC0415"]

[tools.ruff.limits]
C901 = 10
PLR0912 = 12
PLR0915 = 50
PLR1702 = 4

[tools.ruff.options]
target_version = "py312"
preview = true
explicit_preview_rules = true

[tools.flake8]
enabled = true
use_project_config = false
timeout_seconds = 10
plugins = ["flake8-functions"]

[tools.flake8.rules]
select = ["CFQ001"]

[tools.flake8.limits]
CFQ001 = 80

[tools.pylint]
enabled = false
use_project_config = true
timeout_seconds = 10

[tools.pylint.rules]
enable = []
disable = []

[tools.black]
enabled = false
use_project_config = true
timeout_seconds = 10

[tools.mypy]
enabled = false
use_project_config = true
timeout_seconds = 10

[tools.mypy.rules]
enable_error_code = []
disable_error_code = []
```

Для включения или отключения инструмента измените его `enabled`. Чтобы изменить лимит `CFQ001`, отредактируйте:

```toml
[tools.flake8.limits]
CFQ001 = 120
```

При `use_project_config = true` анализатор находит обычную конфигурацию проекта; явно заданные правила и параметры Harness имеют приоритет. При `false` адаптер использует изолированную конфигурацию инструмента. Проходы числовых метрик в обоих случаях остаются изолированными и используют лимиты Harness. Неизвестные настройки, неверные типы, недоступные настроенные плагины и отвергнутые инструментом правила или параметры приводят к ошибке проверки. Валидация конфигурации сообщает путь параметра; ошибки внешних инструментов сохраняют их диагностику.

Ruff принимает `select`, `extend_select` и `ignore`; Flake8 — `select` и `ignore`; Pylint — `enable` и `disable`; MyPy — `enable_error_code` и `disable_error_code`. Поддерживаемые `options` включают целевую версию Python, ограничения длины строк и сложности, режимы форматирования и параметры строгости MyPy. Параметры процессов, вывода и записи файлов контролирует Harness.

У каждого анализатора есть параметр `timeout_seconds`, по умолчанию `10` секунд на один процесс. Он задаётся отдельно от времени выполнения обработчиков в `hooks.json`.

## Ручная проверка файла

Общий анализ Harness можно запускать независимо от Codex. Команда принимает один или несколько путей к Python-файлам и сообщает текущие диагностики включённых анализаторов; сравнение со снимком не выполняется:

```bash
codex-harness-check path/to/file.py
```

Например:

```bash
codex-harness-check \
    project/services/payment.py
```

Если ограничения нарушены:

```text
CODE QUALITY CHECK FAILED
- /project/services/payment.py:1:1: [ruff] F401 `os` imported but unused
- /project/services/payment.py:10:1: [ruff] PLR0915 Too many statements (63 > 50)
- /project/services/payment.py:10:5: [flake8] CFQ001 Function process has length 81 that exceeds max allowed length 80
```

Ruff также можно запустить отдельно:

```bash
codex-harness-ruff path/to/file.py
```

Эта команда использует настройки целевого проекта. Для всех глобальных ограничений Harness, включая `CFQ001` и метрики Ruff, используйте `codex-harness-check`.

Обе команды завершаются с кодом `0`, если диагностик нет, и с кодом `1`, если есть диагностики или ошибки выполнения.

## Проверка самого Harness

После установки текущей версии исходников, как описано в разделе «Установка», выполните из корня репозитория:

```bash
find checks hooks src -type f -name '*.py' -exec codex-harness-check {} +
python3 -m ruff check checks hooks src
python3 -m black --check --target-version py312 checks hooks src
python3 -m mypy --check-untyped-defs --follow-untyped-imports -p codex_harness
```

Эти команды проверяют Python-исходники, форматирование и типы, не изменяя исходные файлы. Команда `find` передаёт отдельные файлы, поскольку `codex-harness-check` не обходит каталоги. Harness использует активную пользовательскую конфигурацию. MyPy проверяет установленный пакет `codex_harness` с его итоговой структурой; после изменения исходников переустановите текущую версию из репозитория. Для `python3` и установленных консольных команд используйте одно окружение Python.

## Блокировка и повторные попытки

`PostToolUse` не откатывает изменение автоматически.

Он возвращает Codex информацию о найденной регрессии.

Например:

```text
Verification failed.
Verification attempt 1/3

Last diagnostics:
Code quality regression detected.

ruff:
- /project/services/payment.py:1:1: F401 `os` imported but unused
- /project/services/payment.py:10:1: PLR0915 Too many statements (63 > 50) [PaymentService.process: 63 > 50]

flake8:
- /project/services/payment.py:10:5: CFQ001 Function process has length 81 that exceeds max allowed length 80 [PaymentService.process: 81 > 80]
```

После этого агент получает конкретную диагностику через `reason` и `additionalContext` и может исправить код следующей итерацией, пока бюджет текущего хода не исчерпан.

### Лимит последовательных неудачных проверок

`max_attempts = 3` в секции `[verification]` допускает максимум три последовательные неуспешные попытки исправления кода в пределах одного пользовательского хода. Если параметр отсутствует, используется `3`. Допускаются только целые числа `>= 1`; логические значения, строки и дробные числа недопустимы.

```text
turn A
patch            → FAIL 1/3
correction patch → FAIL 2/3
correction patch → FAIL 3/3
next apply_patch → denied before changing files

human sends a new message
turn B           → fresh retry budget
patch            → FAIL 1/3
```

После последнего FAIL и при запрете следующего `apply_patch` агент получает:

```text
Verification failed.
Verification attempt 3/3
Retry limit reached for the current turn.

Last diagnostics:
<последняя фактическая диагностика проверки>
```

`PreToolUse` возвращает `permissionDecision: "deny"` до изменения файлов, не создаёт снимок и не увеличивает счётчик попыток. Значение `4/3` не возникает. Запрет распространяется на любой следующий `apply_patch` в той же области выполнения, включая непроверяемые файлы.

Одна попытка расходуется на один патч, фактически изменяющий Python-код и получивший общий результат FAIL, независимо от количества файлов, правил или диагностик. Смена причины отказа, например PLC0415 → F401, не создаёт отдельный бюджет.

Успешная проверка фактически изменённого Python-файла немедленно удаляет `attempts.json` текущей области: `FAIL → FAIL → PASS → FAIL` даёт `1/3 → 2/3 → reset → 1/3`. PASS означает отсутствие новых регрессий относительно снимка до патча и не требует устранения старого технического долга. Изменение только README или другого непроверяемого файла, Python-патч без фактических изменений, повторная доставка hook и обычные действия агента не расходуют и не сбрасывают бюджет. Проверки запускаются только при изменении содержимого или существования отслеживаемого Python-файла.

### Область выполнения и состояние

Область выполнения определяется стабильным SHA-256 от JSON-массива `[session_identifier, resolved_cwd, turn_id]`. Используется `session_id` из входных данных; при отсутствии — `CODEX_THREAD_ID`, затем `CODEX_SESSION_ID`. Для хода требуется непустой корректный `turn_id` во входных данных: общей для сессии или глобальной подстановки нет. Новый ход получает другой каталог, не удаляя состояние предыдущего. Разные сессии и рабочие каталоги также изолированы.

`state/retry/<scope_hash>/attempts.json` содержит только `consecutive_failed_attempts` и `last_failure`. Снимки находятся в том же каталоге; их имена получаются из `tool_use_id`, который не входит в идентификатор области повторных попыток. Снимки прежнего формата непосредственно в `state/` не используются.

Операции защищены файловой блокировкой области выполнения; JSON записывается через временный файл и атомарную замену. PostToolUse забирает снимок переименованием перед проверкой и удаляет его перед сохранением результата. Повторная или конкурентная доставка того же PostToolUse не выполняет проверку заново и не увеличивает счётчик. При прерывании процесса может остаться файл `.processing`; он не обрабатывается повторно.

Состояние прошлых ходов — временные данные выполнения: оно не участвует в новых областях выполнения. Автоматическая очистка этих данных не реализована.

### Ошибки кода и инфраструктуры

Новые или ухудшившиеся диагностики анализаторов, включая синтаксические ошибки изменённого исходника, расходуют попытку исправления. Диагностика содержит файл, строку, колонку и сообщение. Если старый снимок синтаксически некорректен, прежние числовые метрики недоступны; исправленный исходник проверяется по действующим лимитам. Исправление синтаксической ошибки допускается, если оно не создаёт других регрессий.

Невозможность запустить анализатор или плагин, превышение времени выполнения процесса, ошибка файловой системы или прав доступа, неверная конфигурация, повреждённое состояние повторных попыток, некорректный вывод анализатора, внутреннее исключение или неопределимая область выполнения блокируют операцию с инфраструктурной диагностикой, сохраняя счётчик попыток и `last_failure`. Эти результаты не считаются PASS. Синтаксические ошибки исходника распознаются внутри адаптеров; произвольный `SyntaxError` внутри Harness остаётся инфраструктурной ошибкой.

Синтаксические диагностики Ruff с `code: null` и `name: "invalid-syntax"` нормализуются как синтаксические ошибки. Такой формат ответа сам по себе не препятствует исправлению некорректного исходного снимка.

### Подагенты

Если входные данные обработчика содержат `agent_id` или `agent_type`, текущая реализация Harness блокирует патч как инфраструктурную ошибку. Она не выделяет отдельный бюджет повторных попыток и не выводит связь между ходами родительского агента и подагента из PID, времени или истории диалога.

Общий бюджет повторных попыток для подагентов требует надёжного идентификатора корневого пользовательского хода и пока не реализован. Это ограничение текущей интеграции Harness.

Повторные попытки формируются последовательностью вызовов инструментов самого агента. Harness не запускает LLM, агента повторных попыток, собственный цикл агента или финальную обязательную проверку.

## Текущие ограничения

Сейчас Harness ориентирован в первую очередь на Python.

Проверки подключены к:

```text
apply_patch
```

Поэтому текущий процесс проверки качества рассчитан на изменения, которые Codex выполняет через этот инструмент.

Изменения через произвольные команды оболочки пока не входят в этот механизм сравнения.

Также пока не реализованы:

- архитектурные правила ООП;
- правила зависимостей между слоями приложения;
- JavaScript / TypeScript / Vue проверки;
- финальная обязательная проверка через `Stop`;
- проверки всего проекта перед завершением задачи;
- анализ смысла сложных архитектурных изменений.

## План развития

Следующие направления:

```text
Правила ООП и архитектуры
        |
        +-- новые функции вне классов в модулях, организованных вокруг классов
        +-- нарушение существующей структуры проекта
        +-- неправильные зависимости между слоями

Stop hook
        |
        +-- финальная проверка перед завершением задачи
        +-- проверка типов
        +-- проверки всего проекта

Другие языки
        |
        +-- ESLint
        +-- TypeScript
        +-- Vue
        +-- HTML
```

Основная цель проекта — вынести контроль качества кода из вероятностного поведения модели в отдельный детерминированный слой вокруг агента.
